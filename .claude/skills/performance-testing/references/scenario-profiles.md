## VU and Duration Recommendations per Scenario

### Smoke

**Goal**: Confirm the application is alive and returns correct responses under trivial load. Run before every other scenario.

| Parameter | Value |
|-----------|-------|
| VUs | 1–3 |
| Duration | 2 min |
| Ramp | None — flat from start |
| Think time | 1 s |
| Thresholds | Latency and error-rate only — never a throughput floor at 1-3 VUs; any failure here is a blocker |

A failing smoke test means the application is broken, not that it cannot scale. Fix the smoke failure before running load or stress.

### Load

**Goal**: Validate the application behaves correctly at the expected peak concurrent user count.

| Parameter | Value |
|-----------|-------|
| VUs | `--vus` (default 50) |
| Duration | `--duration` min hold after ramp-up (default 10) |
| Ramp | 2 min up → hold → 2 min down |
| Think time | 1–3 s (realistic browsing pace) |
| Thresholds | p95 < 500 ms, p99 < 1 s, error rate < 1%, throughput > the plan's derived `expectedRps` |

The hold period is where steady-state behavior is measured, but k6 thresholds evaluate against every sample collected during the whole run — ramp-up and ramp-down traffic is not automatically excluded. To gate on steady-state behavior only, tag requests emitted during the hold stage and scope the threshold to that tag, or run the hold stage as a separate scenario with its own `startTime`.

### Stress

**Goal**: Find the saturation point where response time climbs or errors spike.

| Parameter | Value |
|-----------|-------|
| VUs | Step-function: 25 → 50 → 100 → 200 → 400 |
| Step duration | 2 min per step |
| Ramp | Instant step-up at each boundary |
| Think time | 0.5 s (compressed to accelerate saturation discovery) |
| Thresholds | Intentionally omit hard thresholds — you want to observe, not gate |

A step-function (rather than a linear ramp) makes the saturation point visible as a discrete cliff in the p99 histogram. Use the results to set your load scenario VU count below the saturation point.

### Spike

**Goal**: Validate behavior when traffic surges to 10× normal in under 30 seconds.

| Parameter | Value |
|-----------|-------|
| VUs | 0 → `--vus` × 10 → 0 |
| Ramp-up | 10 s |
| Hold | 1 min at peak |
| Ramp-down | 10 s (immediate drop to 0) |
| Think time | 0.5 s |
| Thresholds | Same full set as load — p95 < 500 ms, p99 < 1 s, error rate < 1%, throughput > the plan's derived `expectedRps` (see [`agents/implementer.md`](../agents/implementer.md#threshold-rules)) |

A passing spike test means the application queues or rejects excess load gracefully. A failing spike test with increasing error rates means requests are dropped without a proper 429 or 503 response.

### Soak

**Goal**: Detect memory leaks, connection pool exhaustion, or gradual degradation over time.

| Parameter | Value |
|-----------|-------|
| VUs | 20% of `--vus` (default 10) |
| Duration | 60 min minimum; 240 min for production-readiness sign-off |
| Ramp | 2 min up → hold → 2 min down |
| Think time | 2–3 s (realistic pace reduces CPU noise so memory trends are visible) |
| Thresholds | Latency and error-rate as in load, **minus the throughput floor** (10 VUs at 2–3 s think time carries no throughput signal) |

A k6 `thresholds` block evaluates a single condition against the whole run — it cannot compare two
time windows within one run, so "p99 must not increase by more than 20% between the first 5 min
and the last 5 min" cannot be embedded as a script-level gate. Compute it after the run instead:
from `performance/results/soak-<timestamp>.json`, take p99 over samples in the first 5 min and the
last 5 min and compare them, reporting the result alongside the [baseline
comparison](../SKILL.md#baseline-comparison) rather than as an enforced threshold.

Run soak tests on a scheduled CI pipeline, not on every PR. A 60-min soak is appropriate for feature branches; 240-min is appropriate for release candidates.

## Ramp-up vs. Step-function Profiles

**Linear ramp** — VUs increase smoothly from 0 to peak over a fixed period. Use for load and soak tests where you want steady-state measurements without sharp transitions.

```javascript
stages: [
  { duration: '2m', target: 50 },
  { duration: '10m', target: 50 },
  { duration: '2m', target: 0 },
]
```

**Step-function** — VUs jump to a new level and hold for a fixed period before the next jump. Use for stress tests where each step represents a distinct operating condition.

```javascript
stages: [
  { duration: '2m', target: 25 },
  { duration: '2m', target: 50 },
  { duration: '2m', target: 100 },
  { duration: '2m', target: 200 },
  { duration: '2m', target: 400 },
]
```

No ramp-down stage — the run ends at peak so the saturation point stays visible in the final
samples. See [`agents/implementer.md`](../agents/implementer.md) ("Stage configurations per
scenario") for the exact stage list the implementer emits.

**Spike** — ramp to very high VUs instantly, hold briefly, then drop back to zero. Use for spike tests simulating a viral event or a scheduled batch job flood.

Peak VUs are `vuRecommendations.spike.peakVusClamped` — the planner computes `min(peakVus * 10, 500)`
and the implementer reads the result verbatim, never recomputing it. At the default `--vus 50`,
`peakVusClamped` is 500 (already at the cap). At `--vus 1000`, the unclamped value would be 10000
but the planner emits `peakVusClamped: 500`.

```javascript
stages: [
  { duration: '10s', target: 500 },  // vuRecommendations.spike.peakVusClamped
  { duration: '1m',  target: 500 },
  { duration: '10s', target: 0 },
]
```

## Think Time (sleep) Values

Think time simulates the pause between a user receiving a response and initiating the next request. It is not optional — removing it makes VU counts meaningless and produces unrealistic CPU saturation that masks real bottlenecks.

| Scenario | Recommended think time | Rationale |
|----------|----------------------|-----------|
| Smoke | 1 s | Neutral; not measuring capacity |
| Load | 1–3 s | Reflects real browsing pace; adjust based on journey type |
| Stress | 0.5 s | Compressed to accelerate saturation discovery |
| Spike | 0.5 s | Matches stress — speed matters more than realism here |
| Soak | 2–3 s | Slower pace to reduce CPU noise; memory trends are the signal |

For API-only tests where the "user" is another service (not a human): set think time to 0–100 ms to model machine-paced request rates.

## Data Parameterization

### CSV Feeders (k6)

```javascript
import { SharedArray } from 'k6/data';
import exec from 'k6/execution';
import papaparse from 'https://jslib.k6.io/papaparse/5.1.1/index.js';

const products = new SharedArray('products', function () {
  return papaparse.parse(open('./data/products.csv'), { header: true }).data;
});

export default function () {
  const product = products[(exec.vu.idInTest * 7919 + exec.scenario.iterationInTest) % products.length];
  http.get(`${__ENV.BASE_URL}/api/products/${product.id}`);
}
```

`__VU` is assigned once per VU and never changes across its iterations, so `__VU % array.length`
picks the same row every time that VU runs — at most `peakVus` distinct rows get requested no
matter how large the dataset is, and every request after the first is a cache hit. Index on the
iteration counter too (`exec.scenario.iterationInTest`) so each iteration hits a different row; the
prime multiplier spreads consecutive VUs across the array instead of clustering them.

### Environment Variable Lists (k6)

```javascript
import exec from 'k6/execution';

const productIds = __ENV.PRODUCT_IDS
  ? __ENV.PRODUCT_IDS.split(',')
  : ['1', '2', '3'];

export default function () {
  const id = productIds[(exec.vu.idInTest * 7919 + exec.scenario.iterationInTest) % productIds.length];
  http.get(`${__ENV.BASE_URL}/api/products/${id}`);
}
```

Pass via: `PRODUCT_IDS=101,102,103,104,105 k6 run load.k6.js`

### Random Data Generation (k6)

```javascript
import { uuidv4 } from 'https://jslib.k6.io/k6-utils/1.4.0/index.js';

export default function () {
  http.post(`${__ENV.BASE_URL}/api/users`, JSON.stringify({
    email: `perf-${uuidv4()}@test.example.com`,
    name: 'Performance Test User',
  }), { headers: { 'Content-Type': 'application/json' } });
}
```

Use `uuidv4()` for fields that must be unique per iteration (registrations, orders). Use realistic-looking values, not `test123`.

## Authenticated Endpoint Testing

### Token Acquisition via `setup()` (k6)

The `setup()` function runs once before the load test begins. Its return value is passed to every `default()` invocation as the first argument.

```javascript
export function setup() {
  const res = http.post(`${__ENV.BASE_URL}/auth/token`, JSON.stringify({
    username: __ENV.TEST_USER,
    password: __ENV.TEST_PASS,
  }), { headers: { 'Content-Type': 'application/json' } });

  check(res, { 'login succeeded': (r) => r.status === 200 });

  return { token: res.json('access_token') };
}

export default function (data) {
  const params = { headers: { Authorization: `Bearer ${data.token}` } };
  http.get(`${__ENV.BASE_URL}/api/me`, params);
}
```

If `__ENV.AUTH_TOKEN` is set directly, skip `setup()` and use it inline:

```javascript
const params = {
  headers: { Authorization: `Bearer ${__ENV.AUTH_TOKEN}` },
};
```

### Cookie-Based Sessions (k6)

```javascript
export function setup() {
  const jar = http.cookieJar();
  const res = http.post(`${__ENV.BASE_URL}/login`, {
    username: __ENV.TEST_USER,
    password: __ENV.TEST_PASS,
  });
  check(res, { 'login succeeded': (r) => r.status === 302 || r.status === 200 });
  const cookies = jar.cookiesForURL(__ENV.BASE_URL);
  const sessionCookieSet = check(cookies, {
    'session cookie was set': (c) => Array.isArray(c.session_id) && c.session_id.length > 0,
  });
  if (!sessionCookieSet) {
    throw new Error('Login did not set a session_id cookie — aborting before running any unauthenticated traffic');
  }
  return { sessionCookie: cookies.session_id[0] };
}

export default function (data) {
  const jar = http.cookieJar();
  jar.set(__ENV.BASE_URL, 'session_id', data.sessionCookie);
  http.get(`${__ENV.BASE_URL}/dashboard`);
}
```

`cookiesForURL()` returns each cookie name mapped to an **array of raw string values**, not
objects — `cookies.session_id[0]` is already the value; there is no `.value` property to read.
Indexing straight into `.value` silently resolves to `undefined` when the array element is a
string, and throws outright when `cookies.session_id` is missing entirely (e.g. the login response
set no session cookie). The explicit `check()` plus `throw` above fails the run loudly at `setup()`
instead of letting every subsequent request run unauthenticated against `/dashboard`.

## Interpreting k6 Output

After a run, k6 prints a summary block. Key sections:

### `http_req_duration`

```
http_req_duration ..........: avg=142ms min=38ms med=127ms max=1.2s p(90)=221ms p(95)=318ms p(99)=612ms
```

- **avg**: arithmetic mean — misleading when distribution is skewed; prefer p95/p99
- **med**: 50th percentile — half of all requests are faster than this
- **p(95)**: 95th percentile — 95% of requests complete within this time; this is the primary SLA metric
- **p(99)**: 99th percentile — the tail; 1 in 100 requests takes at least this long; relevant for user-visible worst-case experience
- **max**: single slowest request — often an outlier; do not set SLAs against it

### `http_req_failed`

```
http_req_failed ............: 0.23% ✓ 2  ✗ 866
```

The percentage of requests that returned a non-2xx/3xx status code, or where the connection failed. Below 1% is the standard load threshold; below 0.1% for critical payment or auth flows.

### `checks`

```
checks ....................: 98.77% ✓ 8547  ✗ 104
```

`check()` assertions inline in your script. A failing check does not abort the iteration — it only increments the failure counter. Use the `errors` Rate metric with a threshold to cause the run to fail.

### `http_reqs` (throughput)

```
http_reqs ..................: 869    14.48/s
```

Requests per second at steady state. Compare against the plan's derived `expectedRps` for this scenario, not a fixed number — 10 VUs at 2–3 s think time cannot reach 100 req/s no matter how healthy the system is. Low throughput with a high VU count indicates the application is queueing or throttling.

### Threshold results

```
✓ http_req_duration........: p(95)<500ms
✓ http_req_failed..........: rate<1%
✗ errors...................: rate<1% (rate=1.24%)
```

A `✗` next to a threshold means the run exits with a non-zero code. In CI this fails the build.

## Common Performance Anti-Patterns

### Thundering Herd

**Symptom**: Error rate spikes to near 100% during spike tests even at VU counts well below the stress saturation point.

**Cause**: All VUs initialize simultaneously (no ramp), or a cache expiration causes all requests to miss and hit the database at the same time.

**Detection**: Compare spike test error rate at t=0 vs. t=30 s. If errors drop sharply after the first 10–20 s, it is likely a cold-start or cache-miss flood rather than a capacity issue.

**Fix**: Add a slow ramp even for spike tests (10–30 s); implement staggered cache TTL expiry (jitter); use a circuit breaker.

### Connection Pool Exhaustion

**Symptom**: p99 climbs steadily during a soak test while CPU and memory remain flat. Errors increase after 30–60 min.

**Cause**: Database or HTTP connection pools are not returned to the pool (connection leak), or the pool size is too small for the VU count.

**Detection**: Compare p99 in the first 5 min of soak vs. last 5 min. An increase of more than 20% is a warning sign.

**Fix**: Ensure connection cleanup in `finally` blocks; increase pool size to match expected concurrency; add pool wait timeout so requests fail fast rather than queue indefinitely.

### N+1 Query Detection from Load Tests

**Symptom**: p95 increases proportionally as VU count increases during stress tests, even at low VU counts where the database should not be saturated.

**Cause**: Each request triggers N additional queries (one per item in a list), so total DB work is O(VUs × list size) rather than O(VUs).

**Detection**: Compare the ratio of `http_req_duration p95` to `http_reqs rate` across stress test steps. An N+1 pattern shows response time growing faster than throughput. Confirm by profiling DB query counts at different VU levels.

**Fix**: Eager-load related entities; use batch queries; cache list results.

### Missing Think Time

**Symptom**: Load test shows CPU at 100% with only 20 VUs; real production handles 200 concurrent users without issue.

**Cause**: Scripts have no `sleep()`, so each VU loops immediately after receiving a response. 20 VUs without think time can generate the same request rate as 2000 real users.

**Fix**: Always include `sleep(1)` for human-paced journeys; set think time per scenario as documented in this file.

### Hardcoded Credentials or URLs

**Symptom**: Scripts fail in CI because the staging URL differs from the one embedded in the script.

**Cause**: `BASE_URL` or `AUTH_TOKEN` is hardcoded in the script rather than read from environment variables.

**Fix**: All variable configuration flows through `__ENV.*` (k6) or `$processEnvironment.*` (Artillery). The implementer agent enforces this via its mandatory checklist.
