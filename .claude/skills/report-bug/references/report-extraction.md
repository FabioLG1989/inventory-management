# Extracting failures from a test report

A test report is shaped one of four ways. **Sniff it before walking it — never assume which one it is from the file name or path alone**, and check in this order:

1. A JSON object with both `capabilities` and `suites` at the top level is **WebdriverIO** (`wdio-json-reporter`) — Appium when its capabilities target a device. Check this first: it also has `suites`, and read as Playwright it yields nothing.
2. A JSON object with `suites` (and no `capabilities`) is **Playwright**.
3. A JSON object with `testResults` is **Vitest, Jest, or Detox** (all three use the same `testResults[].assertionResults[]` shape — Detox runs its own test files through Jest, so its `--json --outputFile=...` output is byte-for-byte the same shape as a plain Jest unit-test report; one algorithm covers all three, see the Detox note at the end of the Vitest/Jest section below for how to tell them apart).
4. An XML file whose root element is `<testsuites>` or `<testsuite>` is **JUnit XML** — the format nearly every runner can write, including Appium suites in Java (TestNG, JUnit) and Python (pytest).

Anything else is not a supported test-report shape — the boundary described under [`--from-failure <PATH>`](../SKILL.md#input-modes), not a case to guess-parse. When a run wrote both a JSON report and JUnit XML, use the JSON one: it keeps test names intact and carries more evidence.

**Playwright (`suites[]` at the top level, no `capabilities`, not a JUnit `<testsuite>` root):**

1. Descend `suites[]` (recursively — Playwright nests by file/describe block) to each `specs[].tests[].results[]` entry.
2. A failing result has `status: "failed"` or `status: "timedOut"`. Its `error.message` is `actual_result`'s source; `error.stack` is a `stack_trace` evidence entry (write it to a temp file if the adapter needs a path rather than inline text, or pass it as embedded text if the adapter's field accepts it directly — see the adapter's field mapping table).
3. That same result's `attachments[]` array holds the visual evidence. Map each entry's `contentType` to an evidence type and copy `path` through as-is (do not move or re-encode the file):

| `contentType` | evidence `type` | Typical `name` |
|---|---|---|
| `image/png` | `screenshot` | `screenshot` |
| `video/webm` | `video` | `video` |
| `application/zip` | `trace` | `trace` |
| anything else (e.g. `text/plain` stdout/stderr dumps) | `log` | varies |

4. If `attachments[]` is empty (the project didn't configure `screenshot`/`video`/`trace` capture in `playwright.config.ts`), that's expected — proceed with whatever evidence exists rather than treating it as an error.
5. Record `test_reference.framework: "Playwright"`, `.test_name` (the spec's full title — join the describe-block path with the test title the same way Playwright itself displays it, e.g. `"cart.spec.ts › cart subtotal reflects the quantity of a repeated item"`), and `.file` (the spec's `file` path, relative to the project). Keep the failing result's `projectName` (`specs[].tests[].projectName`): with several `projects` in the config, `-g` selects the test once per project, so Phase 2 scopes its re-run with `--project`. Leave `.rerun_command` for Phase 2 to fill in verbatim from the confirmation re-run command it actually used.

Never summarize a `trace.zip`'s contents, and **never write how to open an attachment** (`npx playwright show-trace …`, "unzip and run `npx playwright show-report …`") into any filed ticket, comment, or defect body, in any adapter. Developers already know how to open these files.

**Vitest/Jest (`testResults[]` at the top level):**

1. Iterate `testResults[]` — one entry per test *file*, each holding an `assertionResults[]` array for its individual `it`/`test` cases.
2. A failing entry has `status: "failed"`. Its `ancestorTitles[]` (the `describe` chain) plus `title` build the test name (`fullName` already has them joined, if present); its `failureMessages[]` is an array of one or more assertion-error strings — join them with a blank line if there's more than one, and use the joined text as both `actual_result`'s source and a `stack_trace` evidence entry.
3. There is never an `attachments[]` array and evidence is text-only for a *unit-test* candidate — do not invent a `screenshot`/`video`/`trace` entry, and do not treat the absence as an error. `environment.os`/`.browser` don't apply to a unit test either — it runs in Node (optionally under `jsdom` for DOM-shaped code), not on any particular host OS or browser, so the *host machine's* OS is not meaningful information here. Collapse both into a single `environment.service`-adjacent note instead of printing the OS/Browser lines, e.g. `Runtime: Node/jsdom unit test` (or just `Node` if the project doesn't use `jsdom`) — see the Jira adapter's description template for exactly how this renders. Populate `environment.app_version` from the same commit/branch state as any other source.
4. `suspected_area` comes from the test file's own path plus whatever source file(s) the failure message's stack trace points to (e.g. `js/app.js:141` inside `failureMessages[0]`) — same longest-prefix-match logic against `framework-config.json` as any other input, just sourced from a different field.
5. Record `test_reference.framework: "Vitest"` or `"Jest"` (Vitest's JSON output includes a `vitest` version field near the top level when present; otherwise infer from which one is configured in the project — check for `vitest.config.*` vs `jest.config.*`), `.test_name` (`fullName`, or `ancestorTitles.join(" > ") + " > " + title` if `fullName` is absent), and `.file` (the `testResults[]` entry's `name`, made relative to the project). Leave `.rerun_command` for Phase 2 to fill in verbatim.

**Detox (mobile E2E, same `testResults[]` shape as above):** a `testResults[]` report is a Detox mobile E2E run when a Detox config (`.detoxrc`, `.detoxrc.*`, `detox.config.*`, or a `"detox"` key in `package.json`) sits in the folder of the report's test files or a folder above it, up to the project root — the same configs [run-tests.md](run-tests.md) finds, whatever their extension or folder — not a unit-test run. Apply steps 1-2 above unchanged (same `assertionResults[]`/`failureMessages[]` walk), then diverge on evidence and environment:

- Record `test_reference.framework: "Detox"` (not `"Jest"`/`"Vitest"`, even though the JSON shape is identical to theirs — mislabeling a mobile E2E failure as a unit test loses the distinction a developer needs). `.test_name`/`.file` follow the same rule as Vitest/Jest above.
- `environment.browser` is `null` (there is no browser); populate `environment.os`/`environment.service` with the **device**, not the host machine — e.g. `"Android 14 (Pixel_7_API_34 emulator)"` or the real device model/OS for a physical-device run. Read the device/AVD name from the report's own `configurations`/`device` metadata when Detox includes it, or from the `--configuration` flag used for the run (visible in that Detox config's matching `configurations.<name>.device` entry) when it doesn't.
- Evidence is text-only by default (`failureMessages[]` only, no `attachments[]`) — same as a unit test — **unless** that Detox config configures Detox's own `artifacts` plugin (`artifacts.plugins.screenshot`/`.video`/`.log`), in which case per-test screenshots/videos/device-logs land under `<rootDir>/<run-id>/<test-name>/` (`<rootDir>`: the config's `artifacts.rootDir`, default `./artifacts` beside the config) and should be picked up as `screenshot`/`video`/`log` evidence entries the same way Playwright's `attachments[]` are — check for that directory before assuming there's nothing to attach. **A mobile UI bug with no visual evidence is a materially weaker report than its Playwright equivalent** — unlike a genuine unit test, a Detox failure has a real, visible screen behind it. When the Detox config has no `artifacts` plugin configured, don't silently file text-only: surface it explicitly (a ⚠️ callout on the Phase 4 card, e.g. "no screenshot available — the Detox config doesn't configure Detox's `artifacts` plugin") so the human can choose to add `artifacts.plugins.screenshot`/`.video` (`takeWhen: { testDone: true }` for screenshot is enough for a failure snapshot) and re-run the confirmation before filing, rather than finding out only after the ticket is already created.
- `suspected_area` should include the mobile app's own source path pointed to by the failure (e.g. `App.tsx` for a bare RN app), same longest-prefix-match logic as any other input.

**WebdriverIO / Appium (`capabilities` and `suites[]` at the top level):** `wdio-json-reporter` writes one file per worker (`results-<cid>.json` by default) — read every file the run wrote, not just the first.

1. Iterate `suites[]` — one entry per `describe` block — and each one's `tests[]`. A failing test has `state: "failed"`: its `error` is `actual_result`'s source, and `error` plus `standardError` (the stack) is the `stack_trace` evidence entry. A `hooks[]` entry with `state: "failed"` (a broken `beforeEach`, say) is a failure too — name it after the hook and the suite it ran in.
2. `.test_name` is `<suite name> <test name>` joined with one space — the suite name is only the innermost `describe`, so with nested describes this is the end of Jasmine's `fullName`, which is what the re-run's `--jasmineOpts.grep`/`--mochaOpts.grep` matches against. `.file` is the top-level `specs[]` entry with its `file://` prefix removed, made relative to the project.
3. `capabilities.platformName` of `Android` or `iOS` (or any `automationName` key) makes it an Appium run: record `test_reference.framework: "Appium"`. Without one it is a WebdriverIO browser run: record `"WebdriverIO"`, treat it like Playwright for environment, and stop here.
4. For Appium, `environment.browser` is `null`; `environment.os` is the device, from the same `capabilities` — `platformName`, `platformVersion` when present, and `deviceName`, e.g. `"Android 14 (emulator-5554)"`. Never splice `deviceName` into a shell command to look up a missing version — leave the version out instead.
5. The report itself carries no screenshots. Look for the files a failure hook wrote next to it: `<reports dir>/artifacts/<slug>.png` (`screenshot`) and `<slug>.device.log` (`log` — logcat or the iOS syslog), where `<slug>` is the `.test_name` with every run of characters outside `A-Za-z0-9._-` replaced by `-`, a leading `-` dropped, keeping its last 120 characters. Take the file named `<slug>` or ending in `-<slug>` (the hook names it after the whole describe chain) and written after the run started; with several such files, attach none and say so in the Phase 2 summary rather than guess — the convention the `mobile-e2e-automation-architecture` skill's `wdio.conf.ts` writes. The Appium server log (`wdio-appium.log`, in the folder the Appium service's `logPath` names) covers the whole run: attach it as a `log` entry only when the device log is missing.
6. With no screenshot for the failure, raise the same ⚠️ callout as Detox on the Phase 4 card — "no screenshot available — `wdio.conf` has no failure-screenshot `afterTest` hook" — so the human can add one and re-run before filing.

**JUnit XML (`<testsuites>` or `<testsuite>` root):**

1. Walk every `<testcase>`. A failing one has a `<failure>` or `<error>` child: its `message` attribute is `actual_result`'s source, and the element's text (the stack trace or assertion dump) is the `stack_trace` evidence entry.
2. `.test_name` is the `classname` plus `name` as the runner wrote them; `.file` comes from the testcase's `file` attribute, a `file` `<property>` of its `<testsuite>`, or — for Java — the source file `classname` points to. Some reporters rewrite names (WebdriverIO's JUnit reporter drops characters such as `&`), so a JUnit name may not select the test on a re-run: the [Phase 2](../SKILL.md#phase-2-evidence-gathering) count check catches that.
3. The framework comes from the project, not the XML: `Appium` when it uses an Appium client (`webdriverio` with an Appium `wdio.conf.*`, `<groupId>io.appium</groupId>` with `<artifactId>java-client</artifactId>` in `pom.xml`, `io.appium:java-client` in `build.gradle*`, `Appium-Python-Client` in any letter case in the Python dependencies); otherwise the runner that wrote the file. For Appium, fill `environment` as in step 4 above, from the suite's `capabilities` property or the project's capabilities config.
4. Evidence is text-only, except for files the runner lists in `<system-out>` as `[[ATTACHMENT|<path>]]` lines (the convention TestNG and pytest attachment plugins write) — treat those like Playwright `attachments[]`, typed by extension. For an Appium run, also look for the failure hook's files from step 5 above, and raise the same ⚠️ callout when there is no screenshot.
